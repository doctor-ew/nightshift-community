The task framing accepts the Codex `--json`-always-on change to `scripts/nightshift-factory.sh:475` (`COMMON=(... --sandbox "$SANDBOX" --json)`, replacing the previous verbose-mode conditional) as a delivery tradeoff "to be documented in delivery notes." The regression itself is real and independently confirmed by reading `scripts/nightshift-output.py:120-143`: in `mode == 'verbose'`, a parsed JSON line is only rendered as human text when `verbose_event.get('type')` is `'assistant'`, `'user'`, or `'result'` (Claude-specific event shapes); any other dict — which is now every Codex event, since Codex emits its own `turn.completed`/`item.completed`/etc. shapes, not Claude's — falls to the final `else: print(line, ...)`, printing the raw JSON event instead of legible text. Before this diff, Codex's default verbose mode emitted plain text directly, which that same `else` branch passed through unchanged. **Impact:** default `--output verbose` display for Codex-provider runs now shows raw JSON transcripts instead of readable output — a real, user-visible regression that remains unflagged to the product owner in any shipped doc, contrary to the stated acceptance condition.

### WARN — lens: Big O — confidence HIGH (complexity claim checked honestly per instruction, not glossed as O(n))
`cmd_ingest` (`scripts/nightshift-run-metrics.py:610-659`) calls `_build_ticket_report(directory, receipt["ticket"])` (`:654`) on **every single successful receipt append** — this is the SPEC-mandated "each successful receipt append refreshes the summary best-effort" behavior, not a bug, but its complexity should be stated precisely. `_build_ticket_report` → `_read_ticket_receipts` (`:432-453`) re-reads and re-parses **every** `.json` file under the ticket's `receipts/` directory (all runs, not just the current one) on each call, then `_deduplicate_receipts`, `_partition_overlap`, and `_breakdowns` each do a full O(n) pass over that set. Because this whole O(n) rebuild happens once per ingested receipt, the amortized cost of accumulating N receipts against one ticket over its lifetime (many runs, many role dispatches, many retries — each producing its own receipt) is **O(N²)**, not linear. At realistic per-ticket receipt volumes (tens to low hundreds across a ticket's lifetime) this is not yet a hot-path BLOCK, but it is a real, correctly-described quadratic-in-lifetime cost that will grow with long-running, heavily-iterated tickets and should be tracked rather than assumed away.

Two atomic renames instead of one; no correctness impact, just an avoidable extra fsync/rename per call.
